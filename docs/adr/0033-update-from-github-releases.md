# 更新：整包换掉，源头是 GitHub 的 release

Status: accepted · 已实现

发行版是「解压双击就跑」的一个文件夹，它自己不会长。发一次新版本（`v*` tag → CI 出四个平台的压缩包），
用户手上那份还是旧的：想升级只能自己回 GitHub 找对应的包、重新下载、对照着换文件。
这份包又不止是界面 —— `server/`、`src/core/`、`builtin/` 都在里面，只换 dist 会立刻对不上。
所以需要软件自己认得「有新版本了」，并能把它换上。

## 决定

### 版本的源头只有一处：GitHub 的 release

**盘上的那份**：包根 `version.json`，`scripts/pack.mjs` 出包时从 `package.json` 抄进去（带平台名）。
仓库里没有这个文件 —— 开发模式下就没有「我这一份是哪个版本」这回事，只查不装。

**网上的那份**：`GET /repos/Yogioo/MiCan/releases/latest`。不比 tag 的字面、不认 pre-release，
按数字逐段比（`0.1.10 > 0.1.9`，缺的段当 0）。要装的那份包按名字认：`MiCan-<本机目标>.zip|.tar.gz`，
名字就是 `pack.mjs` 的 `TARGETS` 那一列，一一对应。

**不做**：通道（beta/stable）、增量包、自己挑版本、回滚到上一版。基础版本控制就到这里。

### 一次更新 = 换掉整个包目录

包里没有用户的东西（画布、工作文件夹都在别处），所以更新就是把新包的所有文件盖到旧包上，
**删掉旧版多出来的文件不在这一版管**（`robocopy /E` / `cp -R` 都是这个性子）。版本号相同就不再动。

搬文件的人**不是正在跑的那个进程**：Windows 上 `runtime/node.exe` 锁着，进程不退就换不掉自己。
所以顺序是 —— 后端把包下到临时目录、解好、验出 `server/serve.mjs`，然后写一个几十行的脚本
（Windows 一条 `.bat`、mac / linux 一条 `.sh`）丢到临时目录，脱手拉开它，自己退出：

```
脚本：等这个 pid 消失 → 把 <临时>/pkg/MiCan-<目标>/ 整份盖到包根 → 删掉 <临时>/pkg → 用启动器重新起来
```

等 pid 用系统的现成手段（Windows 是 PowerShell 的 `Get-Process -Id`，mac / linux 是 `kill -0`），
不自己发明握手。删的是 `pkg/` 那一层 —— 脚本自己住在上层，删得掉。它是**唯一**留在临时目录里的东西，
下一次下载开始时会先把整个 `mican-update/` 清掉。

装完重新起来：Windows `start` 一个新窗口跑 `MiCan.bat`、macOS `open MiCan.command`，
用户看到的还是那个「关掉窗口就是停掉 MiCan」；**Linux 只能脱手起**（`setsid nohup`，没有窗口），
那份日志就没有地方看了，这是这条路的代价。

### 手动一条、自动一条

**手动**：设置窗口新增一块「版本」——当前版本、检查更新、立即更新。点更新之后就是上面那套，
跟这个窗口的「保存」无关（它改的不是配置，是软件本身）。

**自动**：全局配置里一项开关，`autoUpdate`，**默认开**（跟这台机器走，不进存档）。
开着时后端自己排：启动 30 秒后问一次，之后每 6 小时问一次；发现新版、且这次发布里有本机那份包，
就先把包下好放一边（预置），再等一个「合适的时候」把上面那条路走掉。
关掉开关只是不自动装，检查与手动那条路照旧 —— 所以关着的时候仍然会问 GitHub，好在有新版本时能说一句。

### 什么时候才敢自动装

装＝重启，而重启会掐掉在跑的一切。两个条件都满足才动手：

1. **手头空着**：没有活跃的运行、也不在进化（跟定时器的「占用」是同一份判据）。
2. **人没在写**：最近 60 秒没有落盘。落盘是防抖的（500ms），刚敲的字一定在盘上；
   等这一分钟是防「重启正好落在人打字的那一下」。

不满足就等 5 分钟再看一眼 —— 不是等到下一个 6 小时，否则一条长链跑一天，永远等不到。

### 装完页面怎么回来

浏览器手上那份 JS 是旧 `dist/` 里的，而 `dist/` 已经被换掉了，所以**必须刷新**。
前端不问「是不是在更新」，它只看事实：`/api/runs` 连着问不到（3 次）就先说一句「正在更新并重启」，
然后每秒问一次，一问到就已经在重开，直接 `location.reload()`。这个判据只有「先连上过后又断掉」才算，
所以后端本来就不在（只起了 vite）时不会被误认成一个死循环刷新。

## Considered Options

- **只换 `dist/`（界面）**：最省事，但后端一变就跟界面配不上，而这次的功能恰好两边都动。
- **不让软件自己搬，只提示「有新版本，去 GitHub 下载」**：那就是今天的现状加一个提示，
  「自动更新」（用户要的默认项）等于没做。
- **原地热换，不重启**：`server/`、`src/core/` 都是进程启动时读进内存的，换了也还是旧的；
  Windows 上 `runtime/node.exe` 更是当场锁着。躲不掉重启。
- **重启后端口顺移**（让新进程接着监听，旧的不动）：那 URL 就变了，用户收藏/打开的地址会失效。
  还是让脚本等旧的退出、占回同一个端口。
- **版本自己造一套（`~/.mican/version`）**：多一处真相；包根那份跟着包走，换文件夹也不会错位。
- **装之前问一句「现在更新吗」**：默认开的自动更新就不是自动了。开关本身已经是那句问话，
  剩下的是「什么算不打扰人」，交给上面那两条判据。

## Consequences

1. `scripts/pack.mjs`：出包时往包根写一份 `version.json`（`{ version, target }`）；`docs/packaging.md` 跟着记一笔。
2. `server/update.mjs`（新）：查 GitHub、比版本、下载解压、写脚本、脱手、退出；以及那个 6 小时的自动圈。
3. `server/api.mjs`：`POST /api/update`（`status` / `check` / `download` / `apply`）；
   `/api/runs` 里捎带一份更新状态（前端每圈就顺手知道了）；记一个「最后一次落盘」的时刻给「人没在写」用。
4. `src/core/settings.mjs`：机器那一层加 `autoUpdate`（默认开）。
5. `src/ui/settings-dialog.mjs`：机器那一层多一块「版本」；`src/ui/main.mjs`：断线重连即刷新。
6. 已知风险：自动装的那一刻，头上有没有人正在干别的（开着进化窗口看、正在框选）不管 ——
   页面一刷新这些现场就没了，但盘上的画布是完整的。人没在写那 60 秒只是把代价压小，不是消除。
7. 已知风险：GitHub 的 API 未鉴权时每小时 60 次，一路「检查更新」点下去会撞上限；
   撞上了就报一句「一小时只能问 60 次」，不影响手上的活。
