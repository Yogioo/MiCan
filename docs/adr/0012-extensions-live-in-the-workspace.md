# 扩展住在工作文件夹里

Status: accepted

节点要能复用，就得有「外部文件写实现、画布扫目录生成菜单」这条路。决定：**一个扩展 = 工作文件夹里的一个目录**（内含 `EXTENSION.md`，见 [ADR-0013](./0013-extension-declaration-is-a-static-manifest.md)）；跨画布复用靠把这个目录拷进目标工作文件夹。**不做用户全局层、不做软件内置层、也不做安装器。**

理由是 MiCan 的性格：工作文件夹是完整的一份 —— 画布、全部 md、全部缓存文件都在里面，「换一个地方打开它，画布就完整回来」。扩展一旦住在工作文件夹之外（`~/.mican/extensions` 之类），这句话就不成立了：换台机器要单独同步那一份，而「这份画布现在跑不跑得起来」变成一条本机依赖 —— 那是最难查的一类问题（第一台机器装了什么，第二台机器没装，画布表现不一样）。

「包」这个概念不必是机制：**一个含多个扩展目录的文件夹就是包**，整包拷进去就是安装。真要从 git 拉，那也是一个命令节点的事。

## Considered Options

- **三层作用域**（软件内置 / 用户全局 / 存档内，存档内优先）：能表达「改一处，五个项目都变」。代价是三处都要有查找顺序、覆盖规则，以及「这份画布上的某个扩展到底来自哪一层」的显示；而 [ADR-0008](./0008-two-layers-of-settings.md) 已经为「设置」付过一次两层的心智成本了。取舍是：现在更贵的是「不敢改、看不见」，不是「改一处要改五处」。
- **只做用户全局层**：跨项目零成本，但上面那句自包含直接没了。
- **软件内置层**：不必存在。命令节点、提取节点、定时器节点是**节点种类**，不是扩展，不需要伪装成扩展塞进菜单。
- **安装器 / registry**：先不做。真要做，也应该是「从一个来源把目录拷进来」，而不是一套版本解析与依赖树。

## Consequences

1. 菜单扫描的根是**工作文件夹**：没有工作文件夹就没有扩展菜单（跟「没有工作文件夹时命令没地方跑」同一个口径）。
2. 换机器 = 带着工作文件夹走 —— 本来就要带，所以没有额外动作。
3. **「同一个扩展被五个画布用」要靠用户自己的手段**（每份画布各存一份，或让五个画布共用同一个工作文件夹）。这是这个决定明确的代价。
4. 扩展目录里的第三方依赖（`node_modules`、`package.json`）归扩展自己：MiCan 不装、不管、不解析。`entry` 写什么就跑什么，那一片自由度归用户。
