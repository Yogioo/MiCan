# 用提取节点封装「从一段文本里取出一个字符串」

ADR-0006 定下「节点的值按标签选路」，但值必须恰好是一个单行字符串 —— 于是每处分叉都得在图里塞一条 shell 命令去把值取出来（`findstr`、`jq`、PowerShell）。这条路在 Windows 的 cmd 上几乎没法维护：命令里的引号会被原样传给被调程序（`findstr /c:"yes"` 搜的是字面量 `"yes"`），`findstr` 命中时输出整行而不是匹配串、不命中时静默 exit 1（而退出码非 0 在这个模型里等于技术失败）；更根本的是，agent 在非交互模式下控制不了自己的 stdout，没法要求它「只打印一行」。

决定：新增第三种节点 —— **提取节点**。它有**取法**（`json:isFull` 这样一段文本），值就是「从源文本里取出来的那个字符串」。源默认是执行来路那个节点的值，有数据入边时用那份文本。取不到（键不存在、不是合法 JSON、取出来是多行）就停并明确报错，不静默给空值。

它的值就是它的全部：执行边拿它选路（ADR-0006 的规则），数据边把它送出去当变量。所以「判断走哪根边」和「把一个字段喂给下游命令」是同一件事的两面，不需要第二套机制。

## 为什么不放在图里当一条命令

跨平台一致（不碰 cmd 的引号规则）、失败模式可控（不是静默 exit 1）、能单测（`pick.mjs` 是纯函数）、不依赖 agent 控制 stdout。而且它照样落一份缓存文件，于是「会跑的节点」这个说法对 `{{名字}}` / `[[名字]]` 两条 token 规则天然成立，零特例。

## Considered Options

- **把「相等」改成「包含」**（边上标签出现在值里就走它）：不用提取器，但误命中要靠「唯一命中才走 + 建边时校验标签互不包含」兜；而且它只解决分叉那一半，变量取值那一半（把多行输出里的一个片段塞进下游命令行）没辙。提取节点让「值恰好是一行键」由节点保证，这条路作废，不再需要。
- **命令节点上加一个「取法」字段**：只动两处（runner 与节点编辑面板），比新节点种类省得多（全仓有 12 处 `kind === 'command'` 的判断）。但那个方案的致命处是**节点的显示输出和它的值对不上** —— 面板上是整份报告、值却是 `yes`，下游为什么拿到 `yes` 没人说得清。多花的钱买的是「值在画布上看得见、还能单独跑看它吐什么」。
- **内置 JSON 解析做成 token**（`{{名字.字段}}`）：能服务所有命令节点，比节点种类的覆盖面大；但 agent 的输出只能当纯文本看，把 JSON 当结构化数据解析这件事本身不成立。
- **判定节点 / JSON 分支节点**（把「取其一个字段」和「分叉」绑在一个新节点上）：分叉本来就是边的能力（ADR-0006），绑在一起会让未来读者以为条件住在节点里。

## Consequences

1. **`kind` 成了三类**。全仓 12 处 `kind === 'command'` 判断逐个过一遍；新增的「会不会跑」判断统一走 `graph.mjs` 的 `runnable(node)`，别再到处写死 kind。
2. **提取节点也落缓存文件**，所以它的值在盘上、`[[名字]]` 拿得到路径。`vars.mjs` 一行没改就支持它 —— 它对「来路不是文本节点」的那一支本来就只看 `result.output`。
3. **取法是一个字段**（`json:isFull`），解析在 `pick.mjs` 一个纯函数里。以后加 yaml 是「多一个分支 + 一次『自己写子集解析还是加依赖』的决策」（项目现在运行时依赖只有 `marked`、`dompurify`），不是零成本。
4. **提取节点当不了入口**，也不能被单独设为入口：没有源就没得取。
5. `FORMAT_VERSION` 3 → 4；2 版和 3 版的存档照旧读得进来。
