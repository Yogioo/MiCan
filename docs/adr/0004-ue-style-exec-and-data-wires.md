# 用 UE Blueprint 式的双流模型组织命令节点

命令节点之间要能一次跑完整条链，而当时把输出灌给下游文本节点这一个动作同时兼任了「顺序」和「传值」两件事，没法表达一条链。参照 UE Blueprint 把控制流与数据流分开的做法。

决定：边分两族。**执行边**连接两个命令节点，只表达先后，不携带数据；一个命令节点的执行输入只收一条，所以执行图是一堆互不相交的直线，没有分叉、没有汇合、没有拓扑排序。**数据边**携带一份文本，两端都可以是命令节点或文本节点；`{{名字}}` 取内容，`[[名字]]` 取那份文件的绝对路径。命令节点上的**入口**标记是链的起点，右键入口跑整条链；另有「运行命令」只跑一个节点，用来单独调试。失败即停。

命令节点的「值」是它的缓存文件（最近一次运行的输出），与文本节点的「值」是它那份 md 对称 —— 两个 token 因此对两种节点是同一个规则。

## Considered Options

- **完整照搬 UE**（引入 Branch / Sequence / ForLoop 一族节点、执行线严格单连接）：那族节点存在是因为 UE 的执行拓扑不能分叉，而我们要的就是没有分叉；引入它们只是把分叉能力加回来。
- **上游输出经临时文件传给下游命令**：缓存文件本来就落盘，不需要临时文件，也不需要跑完即删。
- **上游 stdout 自动接下游 stdin**：让执行边隐含携带数据，两族边就分不干净了。

## Consequences

这是有意偏离 UE 的三处，未来读者不应把它们当 bug 修掉：

1. UE 没有「单独运行某一个节点」，我们保留它作为主要调试手段。
2. UE 的执行流完全无法并行；我们预留一个节点级的「下游并行」开关（已记录、未实现）。
3. UE 的执行从事件节点起跑、数据节点是纯的按需求值；我们的命令节点有副作用，所以数据边取的是上游**最近一次运行**的结果，在链里即这一次，单独跑下游时即上一次。
