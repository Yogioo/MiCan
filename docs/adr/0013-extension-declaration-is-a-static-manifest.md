# 扩展的声明是一份静态清单

Status: accepted

决定：**一个扩展 = 一个目录**，目录里有 `EXTENSION.md`（yaml 头 + 正文）和它自己的实现文件。yaml 头就这几个字段：

```yaml
name: git 状态          # 菜单里显示的名字
description: 把工作目录的 git 状态变成一段 JSON
entry: run.mjs          # 相对扩展目录的入口文件；画布把它拼成绝对路径
args: --repo {{仓库}}   # 可选。{{名字}} 的值从数据入边的标签来
defaults:               # 可选。给输入写默认值，拖出来的节点上先填好
  仓库: my-repo
```

（`defaults` 是后来加的：一开始只有四个字段，然后发现「每拖一个节点都要重新填一遍同样的值」比预想的频繁，于是把默认值也放进清单 —— 拖出来就是填好的。它是缩进的一层 map，也是这个 yaml 头里唯一一层嵌套。）

**扫描只读 yaml 头，不 import 用户的任何代码。** 判据一句话：含 `EXTENSION.md` 的目录就是扩展，是叶子，**不再往下扫**；不含的目录只是菜单里的分组，继续往下 —— 目录层级就是菜单层级。于是「一个目录 = 一个扩展 = 菜单里一项」和「多级子菜单」同时成立，也不会出现「这个目录到底是分组还是扩展」的模糊地带。

正文承载机器不认的东西：JSON 输出长什么样、兜不住时吐什么、重入要求、依赖怎么装。

## Considered Options

- **脚本自己 `export const meta = …`，后端起子进程 `import` 来读**：一份文件就是全部，最贴近「AI 顺手」。但扫描要执行用户代码 —— 死循环挂住菜单、副作用跑在扫目录的时候，还得为此单开一个隔离子进程。静态清单把这些一次性去掉。
- **旁挂 `index.json`**：不执行代码，但两份文件要同步，而「AI 会忘」是必然的（改了脚本忘了改 json，菜单与实现悄悄分叉）。
- **不声明，靠文件名加扫命令行的 `{{}}` 推**：菜单里只剩文件名，没有说明、没有分组，人认不出哪一项是干什么的。
- **`inputs` 字段**：不要。输入名天然活在 `args` 那行的 `{{}}` 里，`collectVars()` 今天就会报「`{{仓库}}` 没有对应的入边」（见 [ADR-0014](./0014-nodes-hold-a-live-reference-to-an-extension.md)）。多一个字段就多一处会不同步的地方。
- **一个目录里放多个声明**：扫描规则就得依赖「目录里随便某个 md」，容易误伤，也和「一个扩展 = 一个动作」对不上。
- **`interpreter` 字段**：先不预支。省了就按 `node` 跑；真到了要 `python` / `npx tsx` 的那天再加一个字段，比现在猜它长什么样便宜。

## Consequences

1. **坏脚本不会把菜单搞挂** —— 扫描根本不碰它，有没有语法错、会不会死循环，都跟菜单无关。
2. 菜单里那一项的全部信息来源就是 yaml 头四个字段，所以「菜单怎么显示」不需要再读别处。
3. `EXTENSION.md` 和 `SKILL.md` 同一套路子（固定文件名 + yaml 头 + 正文），AI 与人都已经熟。
4. 声明是人手写或 AI 写的**普通文本**，MiCan 不改它、也不生成它。
