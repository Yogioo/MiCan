# 让工作流自己进化

Status: direction（方向，不是决定；逐条落地时再各写一份 ADR）

这份文件记的是「用 AI 让编排自己变好」的修改方向。它不描述已经做出来的东西，
只描述该按什么顺序加什么。

## 一句话

现在缺的不是「AI 帮你生成工作流」，而是**运行历史**和**一个能让 AI 改的变化面**。
AI 生成图只是这两样补齐之后自然掉出来的东西，不是起点。

## 两种「麻烦」

「编排麻烦」其实是两件不同的事，要的东西不一样：

| | 症状 | AI 该干的 | 本文哪一段 |
| --- | --- | --- | --- |
| **作者难题** | 想要的链写不出来，连半天 | 图 ⟷ 自然语言（一次性生成） | 「另一条路」 |
| **维护难题** | 链写出来了但不动、老坏，要人手改 | 图自己改自己（持续进化） | 「最小闭环」 |

定为先解决**维护难题**（自进化），下面按它展开；作者难题留在「另一条路」作参考。

## 已经有的前提

别人没有的那一样，MiCan 已经有了：**工作文件夹是纯文本，而且改动面已经定义好了**。

[ITERATE.md](../builtin/workspace/ITERATE.md) 那三层（画布 / 文本节点 / 扩展）实质上就是一份给 AI 的编辑契约：
改链落到 `mican.json`，改提示落到那份 md，改动作落到 `EXTENSION.md` 和它的 entry。
所以「AI 改工作流」这件事**不需要新架构**，只需要补三样现在没有的东西。

### 一、运行历史（已实现，见 [ADR-0020](adr/0020-run-history.md)）

以前只留「最近一次」：`runner` 写 `<节点id>.out` 和它的 `.log`，`results` 每个节点一份，
`scheduler` 的 50 条 hits 只在内存里。**没有历史就没有进化信号** ——
「这条边从来没走过」「这个提取节点连败 8 次」都看不见，AI 会把随机噪声当趋势。

这是唯一不可省的基建。落在 `.mican/runs.jsonl`，一行一次运行：

```json
{"at":1730000000000,"node":"n7","chain":"n1","by":"timer","route":"有单","code":0,"failed":false,"ms":18342,"log":"1730000000000-n7.log"}
```

`chain` 是发起这次运行的节点（入口或定时器；单独跑一个节点就是它自己），`route` 是这一步走的那根执行边的标签，
没往下走就没有这一列。值本身不进这里（值已经在缓存文件和 `<节点id>.out` 里，重复存只会把文件撑大）。
条目按时间追加，不做轮转 —— 真要清，用户自己删。

这一行只看得见节点**外面**：走了哪条分路、成没成、多久。「哪些事代码也能做」藏在节点**里面** ——
比如 pi 的 `.log` 里一轮一轮的工具调用（翻代码、看共享盘、读图）。所以 `runner` 对**每个会跑的节点**，只要有 stderr，
就把 `.log` 按次另存一份（`.mican/runs/<at>-<节点id>.log`），`runs.jsonl` 那一行记上它的文件名。
不分节点种类：以后接 codex cli 之类，只要照扩展约定写，历史自动就有，本体不用为它改。

但 `runner` 只存得下扩展吐出来的东西，信息够不够取决于 stderr 里写了什么。所以要在扩展约定里加一条：
**agent 类扩展把每一步动作写进 stderr，一步一行 JSON**（如 `{"tool":"read","args":{...}}`），各家自己转格式。
这样诊断扩展只写一份解析，不必逐家适配。

体积要留意：agent 的 `.log` 一次可能几百 KB，所以另存的 `.log` 每个节点只留最近 N 次（机器设置 `runLogKeep`，默认 20）。
`.out` 不按次存：诊断用不上，也不做改前改后的输出对比。

### 二、图的可改文本形态

AI 改 `mican.json` 会被噪声带偏：坐标、每跑一次就变的 `results`、看不懂的节点 id，
它想改一根边，却要先在两百行 JSON 里找到那两个节点。

把存档**按性质拆开**，逻辑文件是事实，其余都是它的附属：

| 内容 | 性质 | 放哪 |
| --- | --- | --- |
| 节点的 `id` / `kind` / `command` / `cwd` / `extension` / `consts` / `pick` / `slot` / `schedule` / `file`；`edges`；`settings`；`board` | 逻辑（事实） | `mican.json` |
| `view`；节点的 `x` / `y` / `w` / `h` | 显示 | 另一份布局文件 |
| `results` | 运行产物 | `.mican/` |
| 文本节点的正文 | 内容 | 只在 `docs/` 那份 md |

几条规则：

- **逻辑为准，布局只做补充。** 逻辑里有、布局里没有的节点，打开时自动摆（如上游右边）；布局里多出来的条目忽略。
  AI 只改逻辑文件就够，结构校验也只校它。
- **`results` 移出去**：它每跑一次就变，留在存档里会让每次自进化的 commit 都夹着运行噪声，回滚也会把运行结果一起卷回去。
- **文本正文只留在 md。** 现在正文存在 `mican.json` 的 `text` 里，md 只是存档时写出去的镜像，打开时不读回 ——
  AI 照 ITERATE.md 改 md，下次存档就被盖掉。拆完要反过来：打开时从 md 读正文。
- **节点加一个可读的 `name`，id 不动**：边写成 `from: "n7"`，AI 还得先查 `n7` 是谁，只拆噪声只解决一半。
  id 不改成名字，因为缓存文件、`.log` 和运行历史都按 id 关联，改 id 历史就断了。

这是存档格式的改动：升 `FORMAT_VERSION`、旧存档打开时就地拆开、`server` 的读写和 ITERATE.md 的「画布」层跟着改，
落地时单写一份 ADR。

比起另造一门图语言（一行一根边、render 出来改完再合回去），拆文件让 AI 直接改结构化 JSON，
没有解析和合并这一步，出错面更小。图语言可以留作以后给人看的简洁视图。

### 三、触发与纠偏

不做改前改后的指标对比 —— 生产里要对比就得再跑正常流程，代价太高。改完**直接应用**，效果差靠后续纠偏。

进化有两种触发：

- **自动**：条件可配置，如攒够多少次运行、某节点连败多少次、每天定时。
- **用户**：随时手动触发，可附一段**进化提示词**（遇到的问题），和诊断一起交给 AI。

效果变差时，要么等下一轮自动进化把它改回来，要么用户带着问题触发一次。

## 最小闭环

步骤是固定的，由软件内置的**进化面板**按顺序调（见「用户怎么用」），不在画布上连成链。
诊断和 pi 仍是内置扩展，面板只是按固定顺序调用它们：

```
触发 ──> runs.jsonl ──> 【诊断扩展】 ──> pi 改工作文件夹 ──> 校验 ──> commit + push
                                                              └─ 不过 ─> 回滚
```

1. **落盘运行历史**：上面第一条，已实现（ADR-0020）。改的是 `runner`，不是画布。
2. **诊断扩展**：吃 `.mican/runs.jsonl` 和另存的 `.log`，吐一段 JSON —— 从不走的边、连败的节点、平均步数、
   哪里卡住，以及**多次运行里 agent 都在重复的那串工具调用**（它们是改写成脚本的候选）。
   它同时是**上下文压缩器**：进化每次都要把图和历史塞给模型，
   成本全靠这一步把几千次运行压成十行。
3. **pi**：读诊断（和用户的进化提示词，如果有），
   照 ITERATE.md 直接改**自己的工作文件夹**：改提示词、新写一个扩展（`EXTENSION.md` + entry）把重复的那串动作固定下来、
   加节点连线把它接进链，同时从提示词里删掉让 agent 自己去做的那几句。
4. **校验，过了就存档**：见下「护栏」。

## 全自动，不靠人授权

AI 能改所有三层，包括画布结构（加删节点、连边）和扩展的 `outputs`。人可以参与交流，但流程不依赖人点头 ——
要的就是自进化。

进化的方向是**把 agent 做的事一点点收进脚本**：agent 只留下真要判断的那一步，链才越跑越稳。

### 护栏

校验不管效果好不好，只管**改完这条链还跑不跑得起来**，全是机械检查，写成一个脚本：

1. **改前**：git commit 一份快照。
2. **结构校验**（ITERATE.md 第 4 步那份「做完」清单，外加一条）：
   - `mican.json` 能解析；每根边两端的节点都在；
   - 每个文本节点的路径在 `docs/` 里还在，下游取法（`json:…`）对得上改完的正文；
   - 每个扩展引用的目录里有 `EXTENSION.md`，其 `entry` 指向的文件还在。
3. **新扩展试跑**：接进链之前单独跑一次，stdout 是合格 JSON、声明的出口都有值。
4. **过了**：commit + push。**不过**：回滚到快照，把失败原因交回 AI 重试（次数封顶）。

## 用户怎么用：进化面板

进化做成软件内置的**面板**，不是用户自己搭的链：步骤固定，不给自定义。好处是用户不用搭东西，
也不会出现「AI 改画布时把进化链自己改坏」。

面板上只有这几样：

| 项 | 作用 |
| --- | --- |
| 开关 | 这份工作文件夹要不要自动进化 |
| 触发条件 | 攒够多少次运行、某节点连败多少次、或每天定时；不满足就不进化 |
| 进化提示词 | 一个输入框，写遇到的问题（如「提取老漏掉附件」）；空着就只照诊断改 |
| 立即进化 | 手动触发一次，带上当前的进化提示词 |
| 进化记录 | 每次一条：什么时候、谁触发的、改了什么、为什么（就是那次 commit 的说明），校验没过的也列出来 |
| 撤销 | 在某条记录上点，回退到它之前的快照 |

用起来：

1. 照常搭业务链、跑起来。
2. 打开面板，开自动进化、设条件；或者觉得哪里不对，写一句问题点「立即进化」。
3. 进化完画布、提示词、扩展直接变了，面板上多一条记录说明改了什么。
4. 觉得变差了：点撤销，或者再写一句问题让它接着改。

## 另一条路（作者难题）

如果眼下的疼是「写不出来」而不是「老要人改」，真正的答案不是 AI 帮忙连线，
而是**把分叉从设计期挪到运行期**：

会跑的节点走完一步，不再是「拿值比边上标签」而已，而是失败时把
**失败上下文 + 当前扩展菜单（= 动作空间）**交给一个 agent，让它选一步接上去。边在运行时长出来。

这个更猛也更险：可复现性、可理解性、成本都会掉。护栏至少要有三条 ——
只允许接已有扩展形成的动作、每次自主改图都留痕、用已有的「跑链路最多走多少步」封顶。

它和「把 agent 做的事收进脚本」方向相反：运行时交给 agent 的越多，链越不稳。要稳就不走这条。

## 三个会翻车的地方

1. **改完效果变差，没人发现。** 不做指标对比，就靠下一轮自动进化和用户带着问题触发来纠偏；
   诊断里的连败、卡住要能看出「是这次改动之后才开始的」。
2. **没有历史就进化。** 只看得见最后一次运行，AI 会把偶然当规律。自动触发的条件别设得太松。
3. **改图不可逆。** 快照 + 结构校验 + 自动回滚，三者缺一不可。

## 先做什么

**落盘运行历史（含每个节点按次另存的 `.log`）+ 写一个诊断扩展。** 运行历史已实现（ADR-0020）；
下一步是 agent 类扩展的 stderr 约定，然后是诊断扩展。不动画布、诊断走已有的扩展模型，
而它产生的是后面所有进化都依赖的信号。面板先只做「立即进化」一个按钮，手动跑通一次，再补开关、条件和记录。
